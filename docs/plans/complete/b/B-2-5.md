## Findings (recorded)

### SDK trigger coverage (@clinebot/core 0.0.38, verified against the installed bundle)

The compaction trigger counts **conversation messages only** — the system prompt and tool schemas are excluded from the token count, and `thresholdRatio` is not the effective knob:

1. **Upstream bug: `thresholdRatio` is ignored whenever `reserveTokens` is set.** The trigger fires at `contextWindowTokens - reserveTokens`; the ratio path is only reachable when `reserveTokens` is undefined. Kanban sets `reserveTokens` on every session start (B-2.4), so the ratio is inert. The field is kept in Kanban's config for upstream parity.
2. **Upstream bug: the trigger under-counts the assembled request.** Because system prompt + tool schemas (measured at ~1,297 estimated tokens for the SDK's 5 built-in tools, plus Kanban MCP tools) are excluded, the trigger fires late relative to the provider's real limit. This is why B-2.5 calibrates: `cline-compaction-config.ts` rewrites `contextWindowTokens := limit - est(system) - est(tools)` and folds the safety margin into `reserveTokens`, so the message-only trigger effectively evaluates the full assembled request (system + tools + messages + expected output + margin <= limit).
3. **Upstream bug: `prepareTurn` is never invoked in local mode.** The SDK's compaction pipeline (trigger + basic/agentic strategies + the `compact` callback) is wired through the agent config's `prepareTurn`, but no agent runtime in 0.0.38 calls it. In local mode the compaction config and callback are therefore inert; a long session would still overflow the provider reactively.

Kanban-side guards (this card):

- **Local mode:** `hooks.beforeModel` (`cline-compaction-before-model-hook.ts`) — the agent runtime DOES invoke it before every model request with the fully assembled request. The hook evaluates it against the same calibrated budget (`limit - outputReserve - safetyMargin`) and rewrites the request's messages with the deterministic, model-free compactor when it would exceed the budget. The rewrite is request-scoped: the provider sees a fitting request every turn, the persisted transcript stays complete.
- **Hub mode / future SDK builds:** the `compact` session capability (`cline-compaction-callback.ts`) registered on `localRuntime.compaction.compact` — same deterministic compactor, same calibrated numbers, so when the `prepareTurn` bug is fixed the SDK trigger and the hook never double-compact.

### Safety margin + floors (measured, not copied)

- `safetyMargin = max(4,096 tokens, 10% of limit)` — chars/4 under-counts dense JSON (tool schemas) and provider tokenizers disagree with the estimate; the margin absorbs that drift.
- Calibrated window floored at 1,024 tokens and the message trigger at 256 tokens, so the trigger always has a positive target even when non-message overhead approaches the limit; below that, the B-2.2 overflow-recovery restart remains the backstop.
- Built-in tool schema estimate (1,297 tokens) measured from a real 0.0.38 session request; re-measure on SDK version or built-in tool set changes.

### Follow-up (2026-09-25): turn-based compactor

A live 8-hour run on a local model looped: the agent edited files, then kept investigating
"unexpected" changes and re-installing pnpm. Cause: the original compactor deleted every old
assistant message before any tool result. Assistant messages are small (a tool call plus a little
text), so even a 5% trim removed all of them, and the orphan repair then dropped every tool result.
A 60-turn history went from 114k to about 2.4k estimated tokens, keeping 1 of 60 tool calls.
The beforeModel rewrite is request-scoped (the SDK keeps the full `state.messages`), so this re-ran
on every call once over budget, leaving the model a one-step memory for the rest of the session.

`src/cline-sdk/cline-compaction-turns.ts` now holds one turn-based strategy used by the beforeModel
hook, the `compact` callback and overflow recovery:

- An assistant message and the tool results answering it form one turn. A user text message starts
  its own turn. Dropping a turn never orphans a tool result.
- Turns are dropped oldest-first at chunk boundaries (20% of the target) that depend only on the
  transcript prefix. Consecutive requests keep the same cut, and the provider's prefix cache,
  until the kept tail outgrows the budget.
- The first prompt, the most recent user instruction and the latest turn are kept; truncation is a
  last resort.
- The notice lists what dropped turns did (tool call labels, `(failed)` markers, user
  instructions), bounded to 10% of the target, and states that those file changes are the agent's
  own work. Earlier persisted notices are merged rather than nested.

Same 60-turn history after the fix: a 5% trim keeps 48 of 60 turns (the trim rounds up to the next
boundary).
