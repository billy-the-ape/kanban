## Findings (recorded)

### SDK truncation surfaces (@clinebot/core 0.0.38, verified against the installed bundle)

The SDK's `MessageBuilder` (minified `u4` in `@clinebot/core/dist/index.js`) truncates oversized tool results **at request-assembly time** (`buildForApi`, i.e. when the provider request is built), not at ingestion:

1. **Per-tool cap: 50,000 chars** middle-truncation (`...[truncated N chars]...`) for `read`, `read_files`, `search`, `search_codebase`, `bash`, `run_commands`.
2. **Total-text budget: 6,000,000 bytes** per request, trimming oldest/largest blocks when exceeded.
3. **Read staleness:** re-read files cause earlier read results to be replaced with `[outdated - see the latest file content]`.

This is a request-scoped rewrite: the **persisted transcript keeps the full (multi-MB) content**. Consequences that made an ingestion-time bound necessary:

- Kanban's B-2.3 estimator and the B-2.5 before-model trigger evaluate the persisted/assembled messages and still see the unbounded read, so a single 1 MB read looks like ~250k tokens to the budget even though the SDK would clip it to 50k (~12.5k tokens) at send time.
- For small windows the SDK's own 50k clip is still over budget (12.5k tokens > an 8k window), so the SDK cap alone cannot protect the provider limit.
- The SDK's clip has no artifact reference — the agent has no way to retrieve the clipped content.
- No session/tool-policy config surface exposes or disables these caps (checked `StartSessionInput`/tool policies); there is nothing to tune from Kanban.

This is a capability gap, not an SDK defect: the SDK deliberately keeps its request-assembly caps as a safety net. No upstream issue is filed; instead Kanban's bound is layered **below** the SDK cap (see patch ledger below) so the two never compete — the card's "do not build a second truncator that competes with the SDK's compaction truncation" stop condition is satisfied because the surfaces are complementary (ingestion/persisted vs. request-assembly).

### Chosen route: Kanban-side `afterTool` ingestion bound (no SDK patch)

`@clinebot/agents` invokes `hooks.afterTool` after every tool execution; a `result` returned by the hook **replaces the tool result before the `tool-result` message is persisted**. That is a supported, typed `AgentHooks` surface, so the bound is enforced once, at ingestion, and every later request/estimate sees the bounded message. Verified end-to-end by the integration test (real local `ClineCore` session).

- Hook: `src/cline-sdk/cline-tool-result-bounding-hook.ts` — `computeToolResultBoundChars`, `buildBoundedToolResultExcerpt`, `createClineToolResultBoundingHook`.
- Wiring: `src/cline-sdk/cline-session-runtime.ts` registers it as `agentHooks.afterTool` next to the B-2.5 `beforeModel` compaction hook; `limitTokens` is the session's effective (uncalibrated) window, so the bound scales with the configured provider.
- Scope: read-family tools (`read_files`, `read`) per the card; `CLINE_TOOL_RESULT_BOUND_TOOL_NAMES` is the extension point for B-2.7 (command output / diffs).

### Bound derivation (measured against the SDK, not copied from a constant list)

`boundChars = min(50_000, max(4_000, round(limitTokens × 0.1) × 4))` chars:

- **10% window ratio** — the card's invariant: a single large result must not bypass the budget merely because previous usage was low. At ≤ 10% of the input window, an oversized read can never by itself push an otherwise-empty session over budget.
- **50,000 cap** — mirrors the SDK's request-assembly per-tool cap (finding #1), so a persisted message is never larger than what the SDK would ever send; persisted and sent content stay consistent.
- **4,000 floor** — keeps the excerpt usable for tiny windows; those windows are already covered by the B-2.2 overflow-recovery backstop.
- **chars/4** — the B-2.3 estimator convention; the B-2.5 safety margin absorbs the chars/4 under-count.

Examples: 8k window → 4k chars (floor); 32k → 12.8k; 128k+ → 50k (cap).

### Excerpt + artifact format

- Persisted result: `<head>\n\n...[truncated N chars]...\n\n<tail>` plus a `Full content: <absolute path>` line, all inside the same hard char budget (the reference line reserves its length before head/tail are sized; a fixed-point iteration keeps the marker's own digit width inside the budget). Content that already fits is passed through verbatim — no marker, no artifact.
- Artifacts: `src/workspace/task-artifacts.ts` → `<task worktrees home>/<taskId>/context-artifacts/<toolCallId-sanitized>-<tsMs>-<random8>.txt`, atomic write (lock + temp + rename, `lockedFileSystem`).
- **Placement deviates from the card's first proposal on purpose** (stop condition #2): `<task-workspace>/.kanban/...` would dirty the worktree git status with untracked files, and home-agent sessions have cwd *inside* the checkout, so nothing under cwd is safe. The per-task home (sibling of the worktree state dir) is outside every checkout, and deleting the task state dir removes its artifacts. Artifacts remain on disk until then (deletion safety is B-5).
- Failure mode: artifact write failure → the result is still bounded (excerpt without the reference line) and the failure is logged; the session never breaks on a logging path.
