## Settled decisions

- Precedence with the most-restrictive rule: `effective = min(known positive values)` over {override, metadata}; the **source** is the tier that supplied the minimum (tie → override). If no value is known, `effective = fallback`.
- Fallback constant: `200_000` tokens (matches the SDK unconfigured default, documented as conservative). The 262k figure from B-2.md is a reported ceiling, never a floor and never the fallback.
- Override tier reads `contextWindow` from SDK provider settings (`SdkProviderSettings.contextWindow?` already exists in the SDK schema — no SDK change needed). Later, B-2-9 adds a second override in Kanban settings with precedence *above* this one.
- Until B-2-1's metadata tier is wired, precedence collapses to override → fallback (as B-2.md states).

## Verification

- New unit tests `test/runtime/cline-sdk/context-limit-resolution.test.ts`: override < metadata (min wins, source override), override > metadata (metadata wins), metadata only, override only, neither (fallback 200k), invalid values (0/negative/non-integer) ignored as unknown.
- Harness test: start a session via `cline-session-service-harness.ts`; assert the diagnostic log carries the resolved limit + source.

## Acceptance

- Local model whose server reports 262144 and no override → resolver returns the reported limit, source `provider-metadata`.
- Explicit smaller override (e.g. 131072) always yields 131072, source `override`.
- Source of the selected limit is visible in the session-start log.

## Stop conditions

- SDK `parseSettings` strips `contextWindow` at rest (verify with a round-trip test) → move the override tier to `RuntimeConfigState` (B-2-9 path) and note the decision here.
- Resolver semantics conflict with a B-1 evidence finding (e.g. server enforces a limit different from its metadata) → record the discrepancy; the min rule already handles it.
