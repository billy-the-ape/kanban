## Settled decisions

- Command-output excerpt shape: first N lines + last M lines (default N = M = 100, revisit with measurements) + `... [truncated K lines; full output: <artifact path>]`.
- **Exit status is never truncated away** — later milestones (B-7 deterministic verification) rely on exit status; keep it in the message head.
- Diff results: same mechanism; for large diffs keep per-file stat summary + bounded hunks + artifact path.
- Reuse B-2-6's `src/workspace/task-artifacts.ts`; do not introduce a second artifact store.

2. Apply the same to diff-producing tool results (the Cline loop's diff/git tools as exposed through the SDK host); if the SDK treats them as plain tool results, the B-2-6 tool-result bound may already cover them — prove it with a test rather than assuming.

## Findings (recorded)

### SDK route: reuses B-2.6's `afterTool` hook — no new surface needed

Verified against the installed SDK (`@clinebot/core` 0.0.38 + `@clinebot/agents` bundles):

- The agent runtime passes the **raw** `execute` return value to `hooks.afterTool` as `context.result.output` (no JSON re-stringification), and a `result` returned by the hook replaces the tool result before the `tool-result` message is persisted. B-2.6's `afterTool` hook therefore covers `run_commands` / `bash` directly — same supported, typed `AgentHooks` surface, no SDK patch, no tool-policy surface.
- `run_commands` schema: input `{ commands: string[] }`; output `[{ query, result, success, error? }]`. Non-zero exit carries `success: false` + `error` (`"Command failed: "` + stderr / exit-code text), with partial stdout before the failure kept in `result`. The structured shape survives end-to-end (hook → artifact), so the artifact holds `JSON.stringify` of the raw array.
- The SDK executor spawns `sh` with `maxOutputBytes = 1,000,000` default and appends its own `[Output truncated: …]` notice beyond that. Kanban's per-result bound (≤ 50k chars; typically 4k–12.8k) always sits far below it, so Kanban's excerpt + artifact is the first and only truncation the model sees for command output.

### Excerpt format (B-2.7)

- Per-command meta head is always kept: `Command i/N: <query ≤200 chars>` + `Exit status: success`, or on failure `Exit status: failed — <reason ≤120 chars>` (reason = first line of the SDK error string) — the exit status survives every truncation mode.
- Body: first N / last M lines (default 100/100) separated by `... [truncated K lines; full output: <artifact path>]`, shrunk symmetrically until it fits the B-2.6 per-result char budget (`computeToolResultBoundChars`: 10% of window, 4k floor, 50k cap).
- Char-cut fallback: single-line bodies, or lines too long for any line share → char-based head/tail with `... [truncated K chars; full output: <path>]`; pathological case (marker alone does not fit) → marker cut to the budget.
- Diff bodies: a per-file stat summary computed from the unified-diff headers (`diff --git` + `@@ -a,b +c,d @@` → `+c -a`) is prepended to the head: `Diff summary (N files):` + `  path | +added -removed` (≤ 20 files, paths capped at 120 chars, destination path for renames).
- Non-structured output falls back to the B-2.6 char excerpt; the artifact is B-2.6's `writeTaskContextArtifact` (full structured output including the dropped middle).

### Measured excerpt sizes (8k window → 4,000-char budget)

- ~807 KB / 8,000-line `cat` output → 3,912-char excerpt: 2 meta lines + 19 head lines + marker (7,962 lines omitted) + 19 tail lines; artifact holds the full 806 KB JSON.
- 62 KB / 3,015-line `git diff` (10 lines → 3,000 lines) → 3,988-char excerpt: 4 meta lines (incl. `Diff summary (1 file):  large-file.txt | +3000 -10`) + 87 head lines + marker (2,840 lines omitted) + 88 tail lines; artifact holds the full diff.
- Unit tests pin the unshrunk layout: 1,000 lines at a 4k budget → exactly 2 meta + 100 head + marker + 100 tail = 203 lines.

## Stop conditions

- Same as B-2-6: if no ingestion-time hook exists, the durable fix is the SDK (upstream issue + pinned release); deliver artifact wiring + evidence, park the remainder.
- Bounding must alter the command (e.g. shell-level `| head`) to work → reject that route; it changes what executed and corrupts delivery evidence. Bounding must be on the **result text**, not the command.
