# AM-4: Fenced, audited, restart-safe merge executor

**Status:** implemented. **One implementation PR into `main`.** Depends on: AM-3. Read [README.md](./README.md).

## Deliverable

Implement the **only** code path allowed to write a GitHub PR merge. Trigger it from AM-3's eligible callback. It must not ask an agent to merge or invoke a local git merge/push.

## Write protocol (in order)

1. Accept a typed eligibility decision containing canonical PR, task, access scope, policy revision, exact expected head/base SHA and evaluation time. Treat it as a **candidate**, not authorization.
2. Acquire the existing durable per-PR and head-ref fencing/reservation gate (`src/pr-tracking/pr-reservations.ts`); introduce `auto_merge` operation kind and document interaction with `comment_followup` and `merge_completion`. Never hold the registry mutex during network requests. A single scheduler owner performs writes; second runtime with same storage root must not merge.
3. Under the reservation, re-read task/card/selected PR, policy/arm revision and auth scope. Check there is no live agent writer or pending comment repair. Fetch **fresh, complete** approvals, CI and PR metadata; rerun AM-3 evaluation. Reject any shift in head SHA, base SHA/ref/repository, task selection, policy or approval since candidate evaluation. Fail closed if revalidation cannot finish.
4. Persist a small journal entry **before** invoking GitHub: `attemptId`, `prKey`, `task`, `headSha`, `baseSha`, `policyRevision`, `mergeMethod`, `startedAt`, `state=attempting`, `reason`. Use version-checked, crash-safe storage; record one attempt per immutable evidence identity, not a burst of retries.
5. Make one noninteractive, bounded GitHub REST merge call (`PUT /repos/{owner}/{repo}/pulls/{n}/merge`) with `sha=<validated head SHA>` and allowed `merge_method`, using the established server GitHub authentication. **Never** force-push or use GitHub rules bypass. Honor 403/405/409/422 and merge conflict responses.
6. Regardless of the immediate response (success, error or timeout), fetch the PR again and verify `merged`, `merge_commit_sha` and the expected PR identity. **Only** this remote observation lets the existing merge-completion consumer move Done and dispatch successors. The executor does not directly complete tasks.
7. On clear precondition failure (checks no longer green, review changed, head changed), mark the attempt not merged with a reason and return to ordinary waiting/polling when safe. On permission/policy/configuration failure, persist a terminal **needs attention** reason. On ambiguous timeout, reconcile remote state before any further attempt; never blind-retry the same merge. Release reservation in `finally` only after durable outcome/reconciliation state is persisted.

## Concurrency, crash recovery and audit

- State machine: `idle → attempting → merged_confirmed | waiting | needs_attention`; durable attempt identity and timestamps. On startup, reconcile `attempting` records **by reading GitHub first**, not by repeating writes. Unknown outcomes stay blocked until an explicit recovery action.
- One PR may be linked to multiple tasks, but at most one task/opt-in can own an automatic merge. Distinct task records cannot race for the same PR or remote head branch. Existing merge-completion uses its own reservation after merge is observed.
- Credential changes, repo permissions, dismissed reviews, new commits, draft/closed state, policy changes and user disabling must invalidate pending candidates before write. Cancellation cannot undo a request already accepted by GitHub; surface that limitation accurately.
- Bound every network call and journal; redact secrets and review bodies. Log evidence SHA and blocker codes, not raw tokens. Preserve existing scheduler-lock behavior and rate-limit backoff. Do not create a general-purpose arbitrary-repo GitHub merge endpoint callable by a browser.
- If GitHub native auto-merge is enabled on the PR, avoid a competing write and let the ordinary merged observer handle completion.
- **GitHub enforces additional repository requirements**: a PR can satisfy Kanban's fixed one-approval threshold yet still require two approvals, CODEOWNER review, deployments, or other conditions under GitHub protection/rulesets. Treat a GitHub denial as an actionable blocker, never bypass requirements or repeatedly retry without changed evidence or operator action.

## Required test scenarios

1. One successful merge with expected head SHA, permitted merge method and confirmed post-write remote state.
2. 409 (HEAD moved), 405 conflict, 403 permission, 422 validation, timeout, process crash before/after write, duplicate observations, process restart and stale reservation. Assert no unverified duplicate write.
3. CI turns red, approval dismissed, task disarmed, policy changes, PR closes/turns draft or native auto-merge appears **between** eligible observation and write. Assert no merge call.
4. Competing PRs on a shared remote head, two tasks on one PR, active comment repair, two scheduler owners. Assert serialization and safe recovery.
5. Merge completes but task-completion consumer is temporarily unavailable: task stays In Review until the existing merge-completion path reconciles; successors start only after confirmed merge+durable completion.
6. All tests use injected fake GitHub adapter and temp HOME; **never merge a real repository from CI or local tests**.

## Deployment

Existing Kanban server-side `gh` auth must have repo contents **write** permission to use the merge endpoint, plus checks/reviews read. Ensure `gh auth status` is valid in the **running Kanban server's environment**. No paid subscription, additional workflow or new secret is required. No direct admin bypass; GitHub branch/ruleset restrictions still apply. Existing settings remain off, so installing AM-4 must not merge any existing PR. Roll back by disabling auto-merge flags and stopping the executor; do not roll back merged Git commits automatically.

## Final state (implemented)

- **New `src/pr-tracking/auto-merge-executor.ts`** — the only code path that writes a GitHub PR merge:
  - `computeAutoMergeAttemptId`: one durable attempt per immutable evidence identity (canonical PR key, head SHA, base SHA, policy revision).
  - `createAutoMergeExecutor({ store, getCoordinator, getTaskCard, listBoards, loadPolicy, isTaskWriterActive, adapter, warn, now })` returns `execute(handoff)` and `reconcilePending()`.
  - `execute`: treats the AM-3 handoff as a candidate; reserves the durable `auto_merge` gate (short CAS, never held during network work); under the fence re-reads the live card, record, policy, other claimants, and writer liveness; requests the consumer coalesced fresh evidence read and re-runs the AM-3 pure evaluation. Any precondition drift → `waiting`; permission/policy/configuration blocker codes (`no_policy`, `policy_mismatch`, `no_required_checks`, `auth`, `access`, `unsupported_host`, `malformed_key`) → terminal `needs_attention`; any head/base/policy-revision shift since the handoff → `waiting` (never written). The `attempting` journal is persisted BEFORE the single `gh api PUT …/merge` write; the merge commit is confirmed ONLY by a fresh remote read (bounded `confirmReadBudget`); the durable outcome is persisted before the reservation is released in `finally`.
  - Ambiguous outcomes (write response unconfirmed by the remote read, unresolved reconciliation) leave the journal `attempting` — a later execution or startup reconciliation reads GitHub FIRST, never repeats the write.
  - `reconcilePending` (startup crash recovery): scans all durable `attempting` attempts; merged on GitHub → `merged_confirmed` (with merge commit), still open → demoted to `waiting`, unresolved → stays blocked with a warning. Serialized per-PR through the same in-flight chain as `execute`, takes the SAME durable `auto_merge` fence (skip if another owner holds it), and its journal write is conditional on the entry still being the observed `attempting` identity — it can never drop a live execution's fence mid-write.
  - Duplicate handoffs for the same PR coalesce onto the in-flight execution (single writer per runtime); the durable reservation serializes distinct runtimes on the same storage root.
- **`src/pr-tracking/github-gh-adapter.ts`**: `mergePullRequest(parsed, { expectedHeadSha, mergeMethod })` — one bounded, non-interactive `gh api --method PUT repos/{owner}/{repo}/pulls/{n}/merge` with `sha` and `merge_method` fields (no force-push, no rules bypass); counts against the shared in-flight slot cap; returns `MergeWriteOutcome` (`merged` / `rejected` with HTTP status + redacted detail / `failed` with classified failure). Error details are redacted (token patterns) and bounded. A 403 whose stderr matches the rate-limit pattern (GitHub secondary rate limits) is classified `rate_limit` (transient), not a permission denial.
- **`src/pr-tracking/pr-record-store.ts`**: `setAutoMergeAttempt(prKey, task, attempt)` — version-checked CAS write of the AM-3/AM-4 attempt journal onto the task binding (`autoMergeAttemptSchema`, schema version 1: `attemptId`, identity, `state: attempting | merged_confirmed | waiting | needs_attention`, `reason`, `mergeCommitSha`, `startedAt`, `finishedAt`).
- **`src/core/api-contract.ts`**: `autoMergeAttemptSchema` (+ `AUTO_MERGE_ATTEMPT_SCHEMA_VERSION = 1`) and `githubPrTaskBindingSchema.autoMergeAttempt` (nullable, optional for older records).
- **`src/pr-tracking/pr-reservations.ts`**: `auto_merge` operation kind documented against `comment_followup` / `merge_completion` (serialization: the executor waits while another reservation is held; merge-completion reserves only after the auto-merge write finishes).
- **`src/server/runtime-server.ts`**: ONE shared `createGitHubGhAdapter()` is passed to both the coordinator (reads) and `createAutoMergeExecutor` (the single merge writer), sharing the in-flight cap, rate-limit state, and body digests. The AM-3 `onEligible` callback now hands off to `autoMergeExecutor.execute(handoff)` (fire-and-forget with warning on error). At startup, `autoMergeExecutor.reconcilePending()` runs in the background (a failure warns and retries at the next startup).
- **`src/trpc/pr-tracking-api.ts`**: both `reservePrOperation` and `releasePrOperation` refuse `auto_merge` from the browser (`blocked`: the fence is exclusively owned by the server-side executor — without the release guard, a same-task non-force release would pass `heldByCaller` and clear the durable fence mid-write, and the force liveness probe cannot see the in-process executor) — no browser-triggerable GitHub merge endpoint exists.
- **Tests** (`test/runtime/pr-tracking/auto-merge-executor.test.ts`, 39 cases; `test/runtime/pr-tracking/github-gh-adapter.test.ts` merge-write cases): success path (one fenced write, verified SHA/method, remote confirmation, write-ahead journal, reservation released, task NOT moved by the executor), duplicate-handoff coalescing, idempotence after merge, every precondition-drift class (CI red, approval withdrawn, stale/incomplete evidence, PR closed/draft, head moved, native auto-merge, disarmed, policy revision mismatch, live writer, ambiguous claim, active comment repair, task off board) asserting no merge call, GitHub 409/405/403/451/422, 403-secondary-rate-limit, and adapter timeout/auth/network/rate-limit classification, unresolved remote state keeps `attempting`, serialization against a held `merge_completion` reservation, startup reconcile-vs-live-execute per-PR serialization (fence held at the write) and conditional journal CAS, rejection resilience (rejected execution settles without unhandled rejections and re-executes fresh; a failed reconciliation does not cascade into a queued execution or abort the loop), same-identity retry cooldown (a journaled `waiting` for the same evidence identity does not re-issue the merge PUT inside the 10-minute cooldown, then re-merges after it), 404 merge PUT classified terminal `needs_attention`, startup crash recovery before/after the write (never re-writes), and the task move happening only through the merge-completion consumer. The trpc API suite additionally covers browser `auto_merge` fence exclusivity (non-force AND force release refused, durable fence intact). All fake adapters, temp HOME; no real merges.

## Implementation notes (deviations worth remembering)

- `execute` maps non-eligible re-evaluation with the fixed needs-attention code set to `needs_attention`; every other blocker (drift) is `waiting` because the AM-3 consumer resumes ordinary evaluation and re-arms the handoff when eligible.
- A crashed `attempting` journal for the SAME evidence identity does not block re-execution: the executor reconciles the remote first and, if GitHub confirms still-open, proceeds to a fresh fully re-validated attempt (preserving the first `startedAt`). A terminal `needs_attention` journal for the same identity stays terminal without an explicit operator action.
- Per-PR in-flight chain: `execute` handoffs AND `reconcilePending` jobs serialize per canonical PR (`enqueuePrJob`), so at most one job of the runtime holds (or releases) the durable `auto_merge` reservation at a time. The startup reconcile reserves the SAME fence before reading/writing and its journal CAS only applies while the entry is still the observed `attempting` identity — it can never drop a live execution's fence mid-write or clobber a newer journal entry. The chain is rejection-safe: a failed predecessor never cascades (`prev.catch`), cleanup copies use `then(onFulfilled, onRejected)` so no derived promise rejects unhandled, and `reconcilePending` catches each PR's failure so one bad record cannot abort the loop.
- A journaled `waiting` outcome for the SAME evidence identity blocks re-attempts for a bounded retry cooldown (`AUTO_MERGE_RETRY_COOLDOWN_MS`, 10 min): the AM-3 consumer re-emits the handoff on every ~60 s poll, so without it every 405/409/timeout/rate-limit write failure would re-issue the merge PUT every poll (plan: "never blind-retry the same merge"). Changed evidence (a new attemptId) always attempts immediately. A 404 merge PUT on a fully verified PR path (adapter `not_found`) is a permission/visibility problem → terminal `needs_attention`, never a retry.
- GitHub answers SECONDARY rate limits with HTTP 403: `mergePullRequest` classifies a 403 whose stderr matches `/rate limit|abuse|secondary/i` as a `rate_limit` failure (transient → `waiting`), never as the terminal `github_denied:http_403` needs_attention.
- The confirm/ reconciliation remote reads are bounded (`confirmReadBudget`, default 3) and only ever READ (`refreshPrMetadataOnce`) — the executor never issues a second merge write.
